SECTION 1: STANDARDISATION — WHERE IT HAPPENS (OR DOESN'T)
---------------------------------------------------------------------------

FINDING 1.1 — NO NORMALISATION EXISTS ANYWHERE IN THE PIPELINE
---------------------------------------------------------------
After a full read of every relevant script, there is no StandardScaler,
z-score normalisation, min-max scaling, or any equivalent transform at
any stage of either the synthetic SDE pipeline or the DeepMind pipeline.

Affected files confirmed to have zero normalisation:
  - dataloaders/trajectory_datasets.py    (raw .npy -> float32 tensor, no transform)
  - data_gen/generate_trajectories.py     (saves raw simulated SDE values)
  - data_gen/simulate_true_sde.py         (no post-sim scaling)
  - deepmind/generate_all.py              (saves raw dm_control obs as float32)
  - deepmind/dm_wrapper.py                (flatten_observation: raw concatenation)
  - training/train_meta.py                (trains on raw tensors)
  - adaptation/gated_finetuning_regularized.py  (adapts on raw tensors)
  - deepmind/gated_finetuning_regularized_dm.py (same)
  - All baseline scripts in baselines/

The ONLY form of value transformation in the entire pipeline is the
numerical stability clamp inside simulate_neural_sde_batch:

    x = torch.clamp(x, -x_max_abs, x_max_abs)   # x_max_abs = 10.0

This is a hard clip for SDE explosion prevention, NOT a normalisation step.

NOTE FOR PAPER: The paper_text.txt (Section III.B, Data Preparation)
describes "a two-scalar approach to prevent information leakage" using
separate StandardScaler objects for source and target domains. This
approach IS NOT implemented in the codebase. The paper description must
be updated to match the code, or the scaler must be added.


FINDING 1.2 — STANDARDISATION GRANULARITY: N/A (NONE APPLIED)
--------------------------------------------------------------
Since no normalisation exists, the question of per-dimension vs global
does not currently apply. However, this is a known risk for the DeepMind
experiments (see Section 3 below).

For future implementation, the correct approach for DM Control would be:
  - Fit a per-DIMENSION StandardScaler on the TRAINING split only
  - Apply the same (frozen) scaler to val and test splits
  - Invert the transform when computing RMSE for the methodology.txt

SECTION 2: DATA LEAKAGE ANALYSIS
---------------------------------------------------------------------------

FINDING 2.1 — NO SCALER-BASED LEAKAGE (because no scaler exists)
-----------------------------------------------------------------
There is no risk of fitting a normalisation object on test/validation
data because no such object is created at any point.

FINDING 2.2 — SUPPORT/QUERY SEPARATION IS CORRECT
-------------------------------------------------
The adaptation loop (gated_inference) uses:
  - support set: N_SHOTS=2 trajectories, same theta_id
  - query set:   separate held-out trajectories, same theta_id

The query set is only accessed during the final evaluation block, AFTER
adaptation has completed and the gradient tape has been closed.
No query data influences the z-adaptation or head fine-tuning. CLEAN. ✓

Relevant code path (gated_finetuning_regularized.py, gated_inference):
  1. adapt_model(sde, head, z_init, support, ...)   <- support only
  2. compute_residual(sde, head_opt, z_opt, support, ...) <- support only
  3. gate g computed from support residual           <- support only
  4. simulate on query[:, 0] with no_grad            <- query accessed here only

FINDING 2.3 — GATE VALUE USES SUPPORT RESIDUAL, NOT QUERY RESIDUAL
-----------------------------------------------------------------
The safety gate formula is:
    g = sigmoid(alpha * (tau - D_res))
where D_res = MSE(model_prediction, support_trajectories).
The query set plays no role in gate computation. CLEAN. ✓

FINDING 2.4 — RESUME LOGIC DOES NOT LEAK FUTURE RESULTS
-------------------------------------------------------
The completed_keys set in gated_finetuning_regularized.py reads back
previously written rows and skips tasks already evaluated. The key is:
    f"{regime}_{theta_id}_{steps_available}"
This only checks identity, not metric values. The model weights are not
updated by seeing these rows. CLEAN. ✓

FINDING 2.5 — THETA DISTRIBUTION LEAKAGE: MILD CONCERN
------------------------------------------------------
In config/base_config.py, the test regimes (B and C) are defined by
shifted drift/diffusion means:
  - testB: drift_mean_shift = +0.5, diffusion_mean_shift = +0.5
  - testC: drift_mean_shift = +1.0, drift_std_scale = 2.0

These shift parameters are global constants, not learned from test data.
The test regime shifts are fixed ahead of time, so no leakage. CLEAN. ✓

FINDING 2.6 — RE-NORMALISATION DURING ROLLOUT: DOES NOT OCCUR
-------------------------------------------------------------
Since there is no normalisation, there is no re-normalisation during
rollout. The simulate_neural_sde_batch function operates in the same
raw coordinate space as the training data throughout. CLEAN. ✓

SECTION 3: SCALE AND DIMENSIONAL INTEGRITY — DEEPMIND EXPERIMENTS
---------------------------------------------------------------------------

FINDING 3.1 — HETEROGENEOUS OBSERVATION SCALES IN DM CONTROL
------------------------------------------------------------
DM Control observations are concatenations of physically heterogeneous
quantities from dm_wrapper.py -> flatten_observation():

  Reacher:  [to_target(2D), velocity(2D)]         — similar scale, low risk
  Finger:   [dist_to_target(1D), touch(1D),
             position(2D), velocity(2D)]           — mixed scale, medium risk
  Cheetah:  [position(8D), velocity(9D)]           — velocities can be 10-100x
                                                     larger than positions, HIGH RISK

Without per-dimension normalisation, the training MSE loss is dominated by
high-variance dimensions (typically velocities). The model is incentivised
to match those dimensions accurately while potentially ignoring small-scale
dimensions entirely.

FINDING 3.2 — SUSPICIOUS HARDCODED RESULTS IN plot_benchmark_results.py
-----------------------------------------------------------------------
File deepmind/plot_benchmark_results.py contains HARDCODED results:

  Finger testA  MSE = 3.60e-23
  Finger testB  MSE = 1.70e-19
  Finger testC  MSE = 6.74e-14
  Cheetah testA MSE = 1.42e-17
  Cheetah testB MSE = 5.06e-14
  Cheetah testC MSE = 3.15e-11

Values at 1e-17 to 1e-23 are at or near float32 machine precision
(~1.2e-38 min positive). These are NOT genuine prediction errors.

Most likely cause: dimensional collapse. The NeuralSDE model produces
near-constant outputs (mean-field behaviour), and because there is no
per-dimension normalisation, the aggregate MSE happens to be numerically
tiny in some dimensions while masking large errors in others.

This is exactly the problem that per-dimension RMSE was designed to detect.
See Section 4 for the added metric.

Reacher results (mse_rollout ~ 0.000018 for testA) look plausible and
were presumably computed by deepmind/gated_finetuning_regularized_dm.py
correctly. Finger and Cheetah results are suspect and need re-running with
the per-dimension RMSE metric added in the corrected scripts.

FINDING 3.3 — few_shot_sweep.py AND regime_switch.py ARE STALE
-------------------------------------------------------------
deepmind/few_shot_sweep.py still hardcodes CKPT_PATH = "checkpoints/transfer_epoch_50.pt"
(a synthetic SDE checkpoint, not a DM-Control-specific one) and X_DIM = 10.
This script will silently produce wrong results if run against DM data.

deepmind/regime_switch.py similarly uses the synthetic checkpoint and X_DIM = 10.

Both scripts are effectively superseded by gated_finetuning_regularized_dm.py

SECTION 4: METRIC INTEGRITY — MSE VS RMSE
---------------------------------------------------------------------------

FINDING 4.1 — ALL REPORTED METRICS ARE MSE (SQUARED, DIMENSION-AVERAGED)
------------------------------------------------------------------------
The current metric in both gated_finetuning_regularized.py and
gated_finetuning_regularized_dm.py is:

    F.mse_loss(mean, query)  — mean over batch, time, AND all D dimensions

This is a single scalar that:
  (a) Squares the error, amplifying outlier dimensions
  (b) Averages across all D dimensions, hiding per-dimension collapse
  (c) Has units of [original_unit²], not [original_unit]

This metric can appear misleadingly small if the model collapses on a
subset of dimensions while tracking others, because the collapse contributes
near-zero error to the average.

FINDING 4.2 — ADDED NON-COLLAPSIBLE METRIC: PER-DIMENSION RMSE
-------------------------------------------------------------
The following metrics have been added to both evaluation scripts
(see Section 5 for exact code locations):

  rmse_rollout      = sqrt(mse_rollout)
                      — RMSE over full trajectory, original units, scalar

  rmse_final        = sqrt(mse_final)
                      — RMSE at final step only, original units, scalar

  rmse_per_dim_mean = mean_over_dims( sqrt(per_dim_mse) )
                      — Average per-dimension RMSE. If this is significantly
                        higher than rmse_rollout, dimensional collapse is
                        present (high-variance dims are masking low-error dims
                        in the aggregate average).

  rmse_per_dim_max  = max_over_dims( sqrt(per_dim_mse) )
                      — Worst-case dimension RMSE. A healthy model should
                        have rmse_per_dim_max within ~3-5x of rmse_rollout.
                        A ratio of >100x indicates collapse in that dimension.

Per-dimension MSE is computed as:
    per_dim_mse = ((mean_pred - query) ** 2).mean(dim=(0, 1))  # shape: (D,)

This averages over the batch dimension (multiple query trajectories) and
the time dimension, giving one error per state dimension. Taking sqrt
converts to RMSE in original units per dimension.

Why this is "non-collapsible": even if one dimension has near-zero error
(the model ignores it and it happens to be near-constant), a different
dimension with genuine large error will show up in rmse_per_dim_max and
will also raise rmse_per_dim_mean relative to rmse_rollout.

SECTION 7: ABLATION STUDY DESIGN
===========================================================================

Two ablation axes are implemented in adaptation/ablation_gate_and_latent.py.

---------------------------------------------------------------------------
7.1 GATE MECHANISM ABLATION
---------------------------------------------------------------------------

Three conditions using the default z_dim=16 checkpoint:

  adaptive     Full gate  g = sigmoid(alpha*(tau - D_res))   [Model C]
  always_on    g = 1      Adapted model only; gate removed
  always_off   g = 0      Safe prior z=0 only; adaptation computed but ignored

Expected outcome:
  - 'always_on' should degrade in testC (OOD), where adaptation quality is
    poor. Without the safety gate, the model commits to a bad adaptation.
  - 'always_off' should degrade in testA (in-dist), where adaptation is
    reliable but is being discarded.
  - 'adaptive' should Pareto-dominate both ablations across regimes,
    confirming the gate adds value beyond either extreme.

Output: results/ablation_gate_and_latent.csv  (ablation_axis == "gate")
        results/ablation_summary.png  (left panel)

---------------------------------------------------------------------------
7.2 LATENT DIMENSION SWEEP
---------------------------------------------------------------------------

Three values: z_dim ∈ {8, 16, 32}, each requiring a separately trained
checkpoint. Adaptive gate mode is used throughout.

Checkpoint naming convention:
  z_dim = 8:   checkpoints/meta_zdim8_epoch_50.pt
  z_dim = 16:  checkpoints/meta_epoch_50.pt          (default)
  z_dim = 32:  checkpoints/meta_zdim32_epoch_50.pt

Expected outcome:
  - z_dim=8 may underfit the 10-dimensional SDE family (too compressed).
  - z_dim=32 may overfit or slow adaptation (more parameters to update).
  - z_dim=16 is expected to be Goldilocks for this setting.
  - The sweep validates that results are not cherry-picked at an unusual
    latent size.

Output: results/ablation_gate_and_latent.csv  (ablation_axis == "latent_dim")
        results/ablation_summary.png  (right panel)

Steps sweep used in ablation: [20, 50, 201] (reduced from main sweep to
control runtime; captures start, mid, and full-horizon performance).

---------------------------------------------------------------------------
7.3 GATE CALIBRATION FIGURE
---------------------------------------------------------------------------

Script: evaluation/plot_gate_calibration.py
Input:  results/gated_regularized_final_fixed.csv

Plots gate_value vs residual_error with theoretical sigmoid overlaid.
Because gate_value is computed directly from residual_error, the empirical
correlation is 1.0 by construction. The figure therefore serves a different
purpose than verification: it shows WHERE on the sigmoid curve each regime
operates, and how the gate distributuion shifts across testA → testC.

Key diagnostics:
  testA  gate mean ≈ 0.60  D_res mean ≈ 0.030   16.7% tasks gate < 0.5
  testB  gate mean ≈ 0.44  D_res mean ≈ 0.090   50.0% tasks gate < 0.5
  testC  gate mean ≈ 0.32  D_res mean ≈ 0.179   65.2% tasks gate < 0.5

This monotonic regime trend (testA > testB > testC in gate_mean) is the
key empirical result motivating the adaptive gate design.

Outputs:
  results/gate_calibration.png           — scatter + sigmoid + violin
  results/gate_calibration_by_steps.png  — faceted by support steps

---------------------------------------------------------------------------
8.1  WHAT THIS ANALYSIS DOES
---------------------------------------------------------------------------

Section 4.2 of the paper claims that the test task distribution lies on a
"continuous manifold" relative to the training distribution — i.e. that
structural distance in parameter space predicts generalisation difficulty in
a smooth, monotonic way.  This analysis provides the quantitative evidence.

For each of the 90 test tasks (30 per regime A, B, C), we compute:
  1. Its distance to the training manifold in theta-space (see 8.2)
  2. Its prediction RMSE at 50 adaptation steps
  3. Its safety gate value g at 50 adaptation steps

We then plot all three against the distance in a three-panel figure.

---------------------------------------------------------------------------
8.2  DISTANCE METRIC
---------------------------------------------------------------------------

Each SDE task is parameterised by a Theta object with two weight tensors:

  theta_b     : (x_dim=10, n_drift_basis=8)  — drift coefficients
  theta_sigma : (x_dim=10, n_diffusion_basis=3) — diffusion coefficients

These are concatenated and flattened into a single 110-dimensional vector:

  v(theta) = [ theta_b.flatten() | theta_sigma.flatten() ]

The distance from a test task to the training manifold is defined as the
minimum L2 norm between the test vector and any training task vector:

  d(theta_test) = min_{theta_train in Train} || v(theta_test) - v(theta_train) ||_2

This is a nearest-neighbour distance in the raw (un-normalised) 110-dim
parameter space.  It is a natural measure of structural novelty: a test
task with d ≈ 0 is nearly identical to a training task; a task with large
d requires the model to extrapolate beyond its training distribution.

---------------------------------------------------------------------------
8.3  SCRIPTS
---------------------------------------------------------------------------

  evaluation/proximity_analysis.py
    - Loads data/meta_params.npz via torch.load (weights_only=False)
    - Builds the 150×110 training manifold matrix
    - Computes per-task distances using torch.cdist
    - Merges with gated_regularized_final_fixed.csv at steps=50
    - Saves results/adaptation_with_distances.csv

  evaluation/plot_proximity_synthetic.py
    - Loads results/adaptation_with_distances.csv (distances)
    - Loads results/gated_regularized_final_fixed.csv (metrics at steps=50)
    - Generates results/manifold_distance_analysis.png (3-panel figure)

Both scripts are run from the project root.

---------------------------------------------------------------------------
9.1  AUDIT SCOPE
---------------------------------------------------------------------------

Four adaptation baselines were audited for strict comparability against
Model C (gated_finetuning_regularized.py): MAML (adapt_MAML.py), GRU
warm-start (adapt_gru.py), Weak Transfer (adapt_transfer_weak.py), and
Scratch (adapt_scratch.py).  For each baseline the following properties
were checked:

  (i)   Support information: does the baseline see exactly the same
        support trajectories, limited to limit_steps timesteps?
  (ii)  Optimisation budget: same number of adaptation steps (ADAPT_STEPS)?
  (iii) Evaluation horizon: same full-rollout MSE over all 200 steps from x0?
  (iv)  Adaptation allowed: what parameters/components does each method adapt?
  (v)   Normalisation: consistent with Model C?

---------------------------------------------------------------------------
9.2  FINDINGS AND FIXES
---------------------------------------------------------------------------

FINDING 1 — GRU: evaluation horizon mismatch (CRITICAL, FIXED)
  The old adapt_gru.py evaluated rollout MSE over the LAST 50 steps of the
  query trajectory (rollout_start_idx = query.shape[1] - 51), seeded from a
  mid-trajectory state. Every other baseline and Model C evaluates over the
  full 200-step trajectory starting from query[:, 0, :].  The 50-step
  window is both shorter and easier (warm-started from a true mid-point
  state), making GRU appear artificially better on mse_rollout.

  Fix: changed evaluation in adapt_gru.py to use recursive_rollout(model,
  query[:, 0, :], n_steps=config.time_grid.n_steps=200).  The rollout now
  covers all 201 states (t=0 through t=T) matching every other method.

FINDING 2 — GRU: inconsistent column names (FIXED)
  adapt_gru.py output columns were capitalised ('MSE_Rollout', 'Adapt_Time',
  'NLL') while all other baselines and Model C use lowercase snake_case
  ('mse_rollout', 'adapt_time', 'nll').  The final_comparison.py script
  applied a runtime rename patch, masking the mismatch, but the stored CSV
  was inconsistent and would cause silent errors in any direct join.

  Fix: all output columns in adapt_gru.py renamed to lowercase snake_case.
  Also added 'mse_final' (MSE at the terminal timestep only) for parity
  with MAML, Scratch, and Weak Transfer.

FINDING 3 — Weak Transfer: under-budgeted adaptation (FIXED)
  adapt_transfer_weak.py used ADAPT_STEPS = 20 while Model C, Scratch,
  MAML (inner), and the GRU all ran with an adaptation budget of 50 steps.
  Giving Weak Transfer only 40 % of the optimization budget of its peers
  made it appear weaker than it would be under a fair comparison.

  Fix: ADAPT_STEPS raised from 20 to 50 in adapt_transfer_weak.py.

FINDING 4 — Scratch: head-only adaptation loss (FIXED)
  adapt_scratch.py trained the fresh NeuralSDE+Head using only head MSE
  loss — predicting the final state of the support slice.  Model C uses
  path loss + head loss + L2 regularization on z, providing gradient signal
  from every intermediate timestep.  For Scratch, the SDE weights are fully
  trainable, so full-trajectory path supervision is applicable.

  Fix: adapt_scratch.py now computes loss = loss_path + loss_head where
  loss_path = F.mse_loss(traj_pred, train_data) over the full support
  slice.  This matches the richness of supervision that Model C receives
  during adaptation.  Weak Transfer is exempt: its SDE is frozen, so path
  loss carries zero gradient for the only trainable component (the head).

FINDING 5 — MAML: 5 inner steps vs. 50 for others (NO CHANGE, DOCUMENTED)
  adapt_MAML.py runs INNER_STEPS = 5 with SGD, vs. 50 Adam steps for
  Model C.  This is intentional and methodologically correct: MAML is
  meta-trained with exactly 5 inner-loop gradient steps, and test-time
  inner-loop count must match training for MAML to behave as designed.
  Increasing to 50 steps would violate the MAML contract and invalidate
  the meta-learned initialisation.

  MAML also uses head-only loss (MSE to the final support state) in the
  inner loop — again matching its meta-training objective.  This is a
  structural property of the baseline, not a bug.

FINDING 6 — Adapt_transfer.py (NOT used in final comparison, documented)
  The file baselines/adapt_transfer.py implements a head-only fine-tuning
  baseline using a full encoder+SDE trained by train_transfer.py.  It uses
  a fixed OBS_LEN = 20 for encoder inference regardless of limit_steps, so
  it cannot generate the STEPS_SWEEP results needed for Figure 3.  It is
  NOT listed in evaluation/final_comparison.py and its output
  transfer_head_only_results.csv is not included in any comparison table.
  The actual transfer baseline in the paper is adapt_transfer_weak.py
  (no encoder, z=0, head-only).

FINDING 7 — Normalisation: all baselines consistent (NO CHANGE)
  Model C implements a two-scalar normalisation path (source scaler from
  checkpoint, target scaler fitted on support set), but the existing
  checkpoint (meta_epoch_50.pt) does not contain a source_scaler key.
  As a result, all baselines and Model C operate on raw (unnormalised)
  simulator data.  No inconsistency exists; all methods are on equal
  footing.  The normalisation code is forward-compatible with a retrained
  checkpoint.

9.4  WHAT EACH BASELINE IS ALLOWED TO ADAPT
---------------------------------------------------------------------------

MAML          Full SDE weights + ForecastHead via SGD inner loop.
              Task information is encoded in weights, not in a latent z.
              Uses z = 0 (no encoder) throughout.

GRU           All GRU parameters (backbone + mu/var heads) via Adam.
              Autoregressive: predictions fed back as input at each step.
              No explicit latent code or SDE structure.

Weak Transfer ForecastHead only; SDE and z = 0 are frozen throughout.
              Weakest adaptation: only the output layer is adjusted.

Scratch       Fresh NeuralSDE (hidden=32) + ForecastHead (hidden=32) +
              random z, all trained jointly from random init.  Reduced
              capacity (32 vs. 128 hidden) is intentional to prevent
              overfitting to N_SHOTS=2 trajectories.

Model C       Latent code z + ForecastHead via Adam; SDE weights frozen.
              Retains pre-trained dynamics (SDE) while adapting the
              task-specific representation (z) and output layer (head).
              Safety gate controls how much the adapted model is trusted.

SECTION 11: PERSISTENCE BASELINE (Phase 2 Addition)
Completed: 2026-04-26
Script: baselines/adapt_persistence.py
Output: results/persistence_results_full.csv
===========================================================================

---------------------------------------------------------------------------
11.1  PURPOSE
---------------------------------------------------------------------------

A zero-parameter persistence baseline was added as a mandatory sanity check
for the Phase 2 evaluation rubric.

The baseline requires no pre-training, no adaptation, and no checkpoint.
It is the absolute methodological floor: if any trained model cannot
outperform persistence on mse_rollout, the model has learned nothing
about the dynamics beyond the trivial "last observed value" heuristic.

---------------------------------------------------------------------------
11.2  PREDICTION RULE
---------------------------------------------------------------------------

For a given support slice of length `steps_available`:

  1. Take the final observed state of each support trajectory:
       last_obs_i = support[i, steps_available - 1, :]   for i in N_SHOTS

  2. Average across shots:
       last_obs = mean_i(last_obs_i)                      shape: (D,)

  3. Persist (repeat) this single state across the full 200-step query
     horizon:
       pred[b, t, :] = last_obs   for all b in B_q, t in {0, ..., T-1}

No SDE is simulated. No gradient is computed. Adaptation time = 0.

---------------------------------------------------------------------------
11.3  REPORTED METRICS
---------------------------------------------------------------------------

  mse_rollout   MSE(pred, query) averaged over (B_q, T, D)
  mse_final     MSE(pred[:, -1], query[:, -1])  — terminal step only
  rmse_rollout  sqrt(mse_rollout)
  rmse_final    sqrt(mse_final)
  mse_1step     MSE(pred[:, 1], query[:, 1])    — first predicted step

Because the prediction is constant in time, mse_1step measures the
one-step displacement of the true system from the last observed state,
independent of any model. This provides a natural reference point for
interpreting mse_1step values from trained models (see Section 12).

NLL, gate_value, and residual_error are not applicable and are not
written to the persistence CSV.

---------------------------------------------------------------------------
11.4  DESIGN DECISIONS
---------------------------------------------------------------------------

Shot averaging (rather than picking one shot) is used to reduce variance
from individual noisy support trajectories. For N_SHOTS = 2 the effect is
minor but keeps the baseline principled.

The same STEPS_SWEEP = [20, 40, 50, 80, 100, 120, 201] as all other
baselines is used. This lets the comparison table include persistence
at every context-length operating point.

The output CSV follows the same EXPECTED_COLUMNS schema and lowercase
snake_case naming convention as all other baselines so it can be ingested
by evaluation/final_comparison.py without modification.

SECTION 12: ONE-STEP MSE DIAGNOSTIC (Phase 2 Addition)
Completed: 2026-04-26
===========================================================================

---------------------------------------------------------------------------
12.1  MOTIVATION
---------------------------------------------------------------------------

The Phase 2 evaluation rubric requires tracking one-step MSE as a
diagnostic tool alongside the primary rollout metric.

mse_rollout averages error over all 200 timesteps. This can mask two
distinct failure modes:

  (a) Short-horizon collapse: the model diverges immediately (high
      mse_1step) but the error happens to average out over time.

  (b) Long-horizon drift: the model tracks the first few steps accurately
      but diverges later. mse_1step is low; mse_rollout is high.

Tracking mse_1step separately distinguishes these cases and allows
reviewers to verify that reported mse_rollout improvements come from
genuine trajectory tracking rather than a lucky long-range coincidence.

---------------------------------------------------------------------------
12.2  DEFINITION
---------------------------------------------------------------------------

  mse_1step = MSE(mean_pred[:, 1, :], query_orig[:, 1, :])

where:
  - mean_pred is the Monte Carlo mean trajectory produced by the model,
    shape (B_q, T, D), starting from the true initial state query[:, 0, :].
  - query_orig[:, 1, :] is the true system state at the first simulated
    step after the initial condition.
  - Index 1 (not 0) is used because index 0 is the given initial condition,
    which is identical for model and ground truth by construction.

---------------------------------------------------------------------------

mse_1step at the same (regime, steps_available) cell.

  Model mse_1step << persistence mse_1step:
      The model successfully predicts short-horizon dynamics. Any advantage
      in mse_rollout is likely real.

  Model mse_1step ≈ persistence mse_1step:
      The model is no better than a constant prediction at t=1. Any
      mse_rollout advantage must come from later timesteps; inspect
      rmse_per_dim_max for dimensional collapse.

  Model mse_1step >> persistence mse_1step:
      The model's first step is worse than doing nothing. This signals
      a degenerate rollout (e.g., SDE explosion, wrong initial condition,
      or dimensional collapse on the dominant dimension).

---------------------------------------------------------------------------
13.1  SUMMARY TABLES — mean ± std
---------------------------------------------------------------------------

Script:  evaluation/final_comparison.py
Outputs: results/final_mse_comparison_table.csv          (formatted strings)
         results/final_mse_comparison_table_numeric.csv  (floats, for scripts)

Each cell in the comparison table is formatted as:

    "mean ± std"    e.g. "0.115 ± 0.021"

where:
  mean  = arithmetic mean of mse_rollout across all tasks in the
          (regime, steps_available, Model) cell
  std   = sample standard deviation across those tasks
          (ddof=1, i.e. pandas default)

Both quantities are computed in a single .groupby().agg(mean=..., std=...)
call over the full per-task result DataFrames.  This is the standard
deviation of per-task outcomes, not a standard error; it quantifies
variability across the task distribution rather than uncertainty in the
mean estimate.  Reviewers who want the standard error can derive it as
std / sqrt(n_tasks).

If a cell contains only one task (std = NaN), only the bare mean is
shown.

The numeric float table is saved separately so that downstream scripts
(e.g. gate calibration plots, proximity analysis) can read numeric values
without having to parse "mean ± std" strings.

---------------------------------------------------------------------------
13.2  HERO PLOTS — 95% confidence interval bands
---------------------------------------------------------------------------

Script:  plots/plot_hero_curve.py
Outputs: plots/hero_curve_{testA,testB,testC}.png

Each method is drawn as a solid mean line with a shaded 95% CI band.
The CI is computed as:

    CI half-width = 1.96 × SE,   where SE = std / sqrt(n_tasks)

This is the normal-approximation 95% CI on the mean MSE, which is
appropriate when n_tasks ≥ 20 (the standard task count per regime).

Implementation detail:
  - The raw per-task DataFrames are passed to plot_regime() without
    pre-aggregation. groupby("steps_available").agg(["mean","std","count"])
    is called inside the plotting function.
  - The lower CI band edge is clamped to max(mean - ci_half, mean × 1e-3)
    to prevent zero or negative values on the log-scale y-axis.
  - Custom line colors and styles (from the FILES dict) are applied via
    ax.plot() and ax.fill_between() directly, bypassing seaborn's hue
    machinery so that the existing color/style specification is preserved.

The final_comparison.py plot uses sns.lineplot(errorbar=("ci", 95))
(seaborn's bootstrap CI, 1000 resamples by default) for the multi-panel
comparison figure, which is consistent in interpretation.

---------------------------------------------------------------------------
13.3  RATIONALE FOR SEPARATING std (TABLE) FROM CI (PLOT)
---------------------------------------------------------------------------

The table reports std because it communicates the spread of performance
across the task distribution — a quantity directly relevant to whether a
method is reliable across diverse physics regimes.  A reviewer can inspect
whether Model C's std is smaller than MAML's std to assess stability.

The plot shades CI (= std / sqrt(n)) because CI is the standard visual
encoding for "uncertainty in the depicted mean line".  The std band would
be wider and would overlap substantially between methods, obscuring
mean differences.  CI bands convey the precision of the mean estimate,
which is what the trend lines represent.

Both are reported; neither replaces the other.

SECTION 14: GATE CORRECTION STUDY
Date: 2026-04-26
File: evaluation/gate_correction_study.py
===========================================================================


---------------------------------------------------------------------------
14.1  MOTIVATION
---------------------------------------------------------------------------

The original gate formula uses a fixed raw residual threshold:

    g = sigmoid(GATE_ALPHA * (GATE_TAU - D_res))
    GATE_ALPHA = 20,  GATE_TAU = 0.05

This design is pathological when data variance is large.  In the synthetic
SDE experiments, raw support-set MSE values (D_res) typically fall in the
range 1.1 – 1.6.  With GATE_TAU = 0.05, the argument to sigmoid is always
strongly negative (~20 * (0.05 - 1.3) = -25), yielding g ≈ σ(-25) ≈ 0.

A gate permanently stuck at 0 provides no adaptation signal: the model
always outputs the safe prior regardless of how well it has adapted.  This
is functionally equivalent to "always_off".

The professor's constraint: the threshold must NOT simply be raised.  The
residual must be made dimensionless so that the same threshold τ is
meaningful across tasks and regimes with different data scales.


---------------------------------------------------------------------------
14.2  THREE GATE VARIANTS
---------------------------------------------------------------------------

V1 — ORIGINAL (raw D_res)
  g = sigmoid(20 * (0.05 - D_res))

  Problem: D_res has units of squared state amplitude.  For SDE tasks where
  state values are O(1), D_res ~ 1–2 and the gate is always near zero.
  Expected behaviour: g ≈ 0 for all tasks; adaptation ignored.

V2 — NORMALIZED (NMSE)
  d_norm = D_res / (data_var + 1e-8)
  g      = sigmoid(20 * (0.05 - d_norm))

  data_var is the empirical variance of the support trajectories (scalar,
  not per-dimension).  d_norm is the Normalized Mean Squared Error (NMSE).

  Interpretation: GATE_TAU = 0.05 now means "gate fully opens when the
  adapted model explains ≥ 95% of the data variance".  This is
  dimensionless and scale-invariant.  This variant is used in the deployed
  Model C (adaptation/gated_finetuning_regularized.py).

V3 — ADAPTIVE τ(N)
  tau_n  = GATE_TAU * sqrt(N_steps / N_MAX)    # N_MAX = 201
  d_norm = D_res / (data_var + 1e-8)
  g      = sigmoid(20 * (tau_n - d_norm))

  tau_n is stricter at short horizons (fewer steps → less information →
  require lower NMSE before trusting adaptation) and equals GATE_TAU at the
  maximum step count.  This encodes the prior belief that early in the
  adaptation budget the model should be more conservative.

  At N=201:  tau_n = 0.05 * sqrt(1.0) = 0.05  (identical to V2)
  At N=20:   tau_n = 0.05 * sqrt(20/201) ≈ 0.016  (3× stricter)

REFERENCE MODES (bounds, not variants):
  always_on:  g = 1.0  — pure adapted model, no safety fallback
  always_off: g = 0.0  — pure safe prior, adaptation discarded


---------------------------------------------------------------------------
14.3  SHARED ROLLOUT EFFICIENCY
---------------------------------------------------------------------------

All five modes (V1, V2, V3, always_on, always_off) differ only in the
scalar gate value g.  The final prediction is linear in g:

    pred = (1 - g) * t_safe + g * t_smart

By linearity of expectation the MC average can be split:

    E[pred] = (1 - g) * E[t_safe] + g * E[t_smart]

The script computes t_smart_mean and t_safe_mean once using MC_SAMPLES
draws from the SDE, then evaluates MSE for each g value analytically.
This costs 2×MC_SAMPLES SDE rollouts instead of 5×MC_SAMPLES.

Each STEPS_SWEEP value [20, 50, 100, 201] triggers a fresh z encoding:

    enc_len = min(steps, 50)
    z_init  = encoder(support[:, :enc_len]).mean(0, keepdim=True)

The adaptation loop runs for ADAPT_STEPS gradient steps starting from
z_init.  D_res (support-set MSE after adaptation) and data_var are
computed on the same support slice used for encoding, ensuring no
query-set leakage.

    This confirms the original gate is broken for scaled data.  The raw
    threshold is not meaningful without normalization.

    Normalization works.  testA tasks (in-distribution) should have lower
    NMSE → higher gate; testC tasks (OOD) should have higher NMSE → lower
    gate.  This validates the safety mechanism: the gate automatically
    reduces trust when the task is novel.

If V3 < V2 at low step counts:
    Adaptive τ(N) is more conservative early in adaptation, as intended.

If V2 MSE < V1 MSE:
    Normalization improves task performance by allowing the adapted model
    to contribute, rather than always falling back to the safe prior.

If always_on MSE > always_off MSE for testC:
    Adaptation overcorrects on OOD tasks without the safety gate, validating
    the necessity of the gating mechanism.

SECTION 15: REGIME-SWITCH EXPERIMENT
Date: 2026-04-26
File: evaluation/regime_switch_experiment.py
===========================================================================


---------------------------------------------------------------------------
15.1  PURPOSE
---------------------------------------------------------------------------

The regime-switch experiment answers the question: "How quickly does the
model detect and adapt to a sudden, unannounced change in the underlying
physics?"  This is a stress-test beyond the standard few-shot evaluation:
the model receives no explicit signal that the regime has changed — it must
infer the shift purely from the incoming observation stream.

The experiment also provides visual evidence for the "continuous manifold"
claim: a model with a well-structured latent space should show a smooth,
monotone trajectory of the latent norm ||z_t|| after the shock, tracking
the new regime rather than oscillating or collapsing.


---------------------------------------------------------------------------
15.2  EXPERIMENTAL PROTOCOL
---------------------------------------------------------------------------

For each of N_SEEDS=5 independent (taskA, taskC) task pairs:

STEP 1 — "Hard Shock" trajectory construction
  A "Frankenstein" ground-truth sequence is built:
      gt = traj_A[:T_PRE] || traj_C[:T_POST + 1]
  where:
      T_PRE  = 50   (steps of testA physics before the switch)
      T_POST = 100  (steps of testC physics after the switch)
  This is intentionally adversarial: both the hidden state AND the
  underlying physics change instantaneously at index T_PRE.  There is no
  warm-up period for the new regime.

STEP 2 — Online sliding-window inference
  A sliding context window of CONTEXT_LEN = 20 observations is maintained.
  At each step t ∈ [CONTEXT_LEN, T_PRE + T_POST):
      context  = gt[t - CONTEXT_LEN : t]             shape (CONTEXT_LEN, D)
      z_t      = encoder(context.unsqueeze(0))        online re-encoding
      x_pred   = gt[t] + SDE.f(0, gt[t], z_t) * DT  Euler step (DT = 0.005)
      mse_t    = MSE(x_pred, gt[t + 1])              per-step error
      ||z_t||  = L2 norm of the latent vector         latent norm

  The encoder is not fine-tuned during this loop; adaptation occurs
  purely through the changing context window content.

STEP 3 — Per-seed metrics

  Let errors[i] denote mse_t at position i in the flattened errors array,
  where position 0 corresponds to absolute step CONTEXT_LEN and the shock
  falls at position SHOCK_IDX = T_PRE - CONTEXT_LEN = 30.

  pre_errors  = errors[:SHOCK_IDX]       (30 measurements, pre-shock)
  post_errors = errors[SHOCK_IDX:]       (100 measurements, post-shock)

  baseline_mse   = mean(pre_errors)

  Peak Shock Error
      = max(post_errors)
      Definition: the single worst per-step prediction error in the
      post-shock window.  A model with a rigid latent space will show a
      large spike immediately after the switch.

  Mean Recovery Time
      = argmin_{i ∈ [0, T_POST)}  { post_errors[i] <= baseline_mse }
        (sentinel value T_POST = 100 if the condition is never met)
      Definition: the number of steps after the regime switch until the
      per-step MSE returns to its pre-shock average level.  Smaller is
      better; T_POST means the model did not recover within the observation
      window.

STEP 4 — Aggregation
  Both metrics are averaged across N_SEEDS pairs.  The std is reported as
  the uncertainty measure, consistent with the rest of the evaluation
  (see Section 13).

  Reported as: "Peak Shock Error = mean ± std"
               "Mean Recovery Time = mean ± std steps"


---------------------------------------------------------------------------
15.3  LATENT NORM TRAJECTORY
---------------------------------------------------------------------------

The L2 norm of the latent code ||z_t|| = sqrt(sum_i z_i^2) is tracked at
every step of the online inference loop.  Its trajectory reveals whether
the encoder's representation actively shifts in response to the new physics.

Expected behaviour:
  Pre-shock (t < T_PRE):  ||z_t|| is approximately stable.  The context
      window contains only testA data; the encoder outputs a consistent
      latent code for those dynamics.

  Post-shock (t >= T_PRE):  ||z_t|| begins to change as the sliding window
      fills with testC observations.  The norm may increase (if testC tasks
      require larger coefficients) or decrease, but should show a monotone
      trend rather than noise.  The speed of this transition reflects the
      model's effective "memory horizon": full adaptation is reached after
      approximately CONTEXT_LEN = 20 steps, when the window contains only
      testC data.

  Latent norm convergence:  If the latent norm plateaus at a new stable
  value within CONTEXT_LEN steps of the shock, this validates that the
  encoder is operating in a well-organised latent space where testA and
  testC tasks occupy distinct, stable regions.  Oscillation or failure to
  converge would indicate latent space entanglement.

The latent norm trajectory is plotted in Panel B of the figure alongside
the shock line and recovery window, making the timescale of adaptation
directly comparable to the timescale of error recovery.

---------------------------------------------------------------------------
15.6  RELATIONSHIP TO OTHER SECTIONS
---------------------------------------------------------------------------

This experiment is complementary to the manifold distance analysis
(Section 14 of README, evaluation/proximity_analysis.py):
  - Proximity analysis measures static distance: how far is a *fixed* test
    task from the training distribution?
  - Regime-switch measures dynamic adaptation: how quickly does the model
    track a *moving* task that transitions from near to far?

Peak Shock Error is expected to be higher for task pairs where testC lies
farther from the training distribution (larger theta-space distance).
Mean Recovery Time is expected to be approximately CONTEXT_LEN = 20 steps
for a model with a well-structured latent space, since full context refresh
requires that many new observations.
